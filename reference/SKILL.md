# 코드 설명서 작성 지침

## 1. 목적

코드 설명서는 독자가 코드 1개를 이해하게 하는 문서다.
코드 설명서는 예시 값을 정한다. 코드 설명서는 예시 값이 코드를 지나며 바뀌는 과정을 보여 준다.
독자가 예시를 처음부터 끝까지 따라 읽으면, 독자는 아래 4가지를 이해한다.

1. 큰 틀: 구성 요소와 구성 요소 사이의 관계
2. 큰 흐름: 실행 순서와 갈래
3. 코드 원리: 코드 줄마다 하는 일과 개념
4. 데이터 모양: 단계마다 들어가는 데이터와 나오는 데이터의 실제 값

독자는 배경지식이 없다고 가정한다.

## 2. 작업 순서

1. 범위를 정한다 (3절).
2. 코드를 읽는다 (4.1절).
3. 예시를 정한다 (4.2절).
4. 예시 값을 따라간다 (4.3절).
5. 문서를 쓴다 (5절, 6절, 7절).
6. 문서를 점검한다 (8절).
7. 파일 `<대상 이름>_코드설명서.md`를 사용자에게 보낸다. 응답에는 추정한 값과 중요한 주의 사항만 쓴다.

## 3. 범위

1. 모드를 정한다.
   - 스크립트 모드: 지정한 파일 전체를 설명한다.
   - 흐름 모드: 진입점 1개에서 호출하는 코드만 설명한다.
2. 사용자가 모드를 정하지 않았으면, 사용자에게 1번 묻는다.

## 4. 준비

### 4.1 코드 읽기

1. 진입점을 찾는다.
2. 갈래를 찾는다. 갈래는 실행 경로가 나뉘는 지점에서 생긴다. 예: 실행 인자 분기.
3. 갈래마다 호출 순서를 함수 이름, 줄 번호와 함께 적는다.
4. 코드가 읽는 파일, 입력, 전역 값을 적는다.
5. 코드가 키나 속성으로 접근하는 데이터 구조를 적는다.

### 4.2 예시 정하기

1. 예시를 2~4개 정한다. 예시 이름은 "예시 1", "예시 2"로 쓴다.
2. 예시마다 갈래 1개를 지나가게 한다. 갈래가 1개뿐이면, 조건이 다른 예시를 2개 이상 정한다.
3. 첫 예시는 중심 갈래를 지나가게 한다. 다음 예시는 앞 예시가 지나가지 않은 코드를 지나가게 한다.
4. 모든 예시를 합치면, 범위 안 코드의 주요 줄을 모두 지나가게 한다.
5. 예시마다 상황 1문장과 입력 값을 정한다.
6. 모든 예시에서 같은 예시 데이터 세트를 쓴다.
7. 예시 데이터에는 실제 업무 내용을 넣는다. 좋은 예: `"title": "월간 매출 집계"`. 나쁜 예: `"title": "abc"`.
8. 예시 데이터는 코드가 접근하는 키를 모두 포함한다.
9. 예시 데이터는 조건 분기를 지나가게 정한다. 예: 길이 제한을 넘는 텍스트 1개.
10. 긴 데이터는 앞부분, 반복 패턴, 길이만 정한다.

### 4.3 값 따라가기

1. 예시 값을 진입점에 넣는다.
2. 코드를 한 줄씩 읽는다. 줄마다 변수의 값을 적는다.
3. 단계 N의 출력을 단계 N+1의 입력으로 쓴다.
4. 수치는 계산 스크립트로 구한다. 예: 글자 수 합계, 나눗셈의 몫.
5. 코드가 없는 외부 함수는 출력을 추정한다. 근거는 함수 이름, 호출 방식, 주석, 반환값을 쓰는 줄이다.
6. 추정한 값에는 "(추정)"과 근거 줄 번호를 쓴다.

## 5. 문서 구성

문서는 Markdown 파일 1개다. 다이어그램은 mermaid로 그린다.
문서는 아래 순서로 쓴다.

| 순서 | 절 | 하는 일 |
|---|---|---|
| 1 | 제목과 첫 문장 | 대상을 알린다 |
| 2 | 큰 틀: 구조도 | 구성 요소와 관계를 보여 준다 |
| 3 | 큰 흐름: 실행 순서 개요 | 갈래와 갈래별 출력을 보여 준다 |
| 4 | 예시 데이터 | 코드가 읽는 데이터의 모양을 보여 준다 |
| 5 | 예시 1, 예시 2, … | 예시 값으로 코드를 단계별로 따라간다 |
| 6 | 주의할 점 | 실수하기 쉬운 코드를 알린다 |
| 7 | 범위 밖 | 설명하지 않은 코드를 알린다 |
| 8 | 각주 | 긴 개념 설명을 모은다 |

### 5.1 제목과 첫 문장

1. 제목은 `# <대상 이름> 코드 설명서`로 쓴다.
2. 제목 아래에 "이 문서는 <대상 이름>을 설명하는 자료이다."를 쓴다.
3. 그 다음에 바로 구조도 절을 쓴다.

### 5.2 큰 틀: 구조도

1. `flowchart`로 그린다.
2. 구성 요소를 층별 `subgraph`로 묶는다. 층은 진입, 갈래 처리, 도우미, 외부 모듈, 데이터다.
3. 함수 노드 라벨: 1줄은 함수 이름, 2줄은 하는 일이다.
4. 데이터 노드 라벨: 1줄은 데이터 이름, 2줄은 내용 요약이다. 예: "node 3개의 상태".
5. 호출 선에는 넘기는 값을 쓴다. 데이터 선에는 동작과 내용을 쓴다. 예: `-.->|"읽음: node 상태"|`.

### 5.3 큰 흐름: 실행 순서 개요

1. `flowchart TD`로 그린다.
2. 진입점에서 갈래로 나뉘는 부분만 그린다.
3. 갈래 노드 라벨: 1줄은 갈래와 예시 이름, 2줄은 하는 일, 3줄은 최종 출력 요약이다.

### 5.4 예시 데이터

1. 코드가 파일을 읽으면, 파일 위치를 트리로 쓴다.
2. 데이터마다 업무 내용 1문장, 예시 값, 데이터를 읽는 예시와 단계 번호를 쓴다.
3. JSON은 `jsonc` 코드 블록에 쓴다. 키마다 `//` 주석을 쓴다.
4. 새 용어는 이 절에서 처음 나올 때 뜻을 쓴다.

### 5.5 예시

예시마다 아래 순서로 쓴다.

1. **상황**: 상황 1문장과 입력 값
2. **시퀀스 다이어그램**: 단계 순서와 넘기는 값을 보여 준다 (6.2절).
3. **데이터 변환도**: 데이터 모양이 3번 이상 바뀌는 예시에만 넣는다 (6.3절).
4. **단계 설명**: 시퀀스 다이어그램의 번호 순서로 쓴다 (5.6절).
5. **예시 결과**: 최종 출력과 부수효과

앞 예시에서 설명한 코드가 다시 나오면, 앞 예시의 단계 번호를 쓴다. 이번 예시의 입력 값과 출력 값은 다시 쓴다.

### 5.6 단계 설명 양식

````markdown
#### ⑨–⑫ `status_summary(root)`: 현재 상황 요약을 만든다

위치: `파일명:26-72`

**이 단계에서 하는 일**
1~3문장.

**들어가는 데이터**
```jsonc
// 실제 값. 키마다 주석
```

**코드와 주석**
```python
원본 코드        # ← 이 줄이 하는 일
                 # [개념] 개념 이름: 설명 1문장
```

**값 추적**
1. 중간 값을 순서대로 쓴다.

**나오는 데이터**
```text
실제 값
```

**다음 단계**: ⑬ `gf.context_block()`이 이 출력을 받는다.
````

1. 단계마다 원본 코드를 넣는다. 생략한 줄은 `# … (40–41행 생략: 빈 그래프 처리)`로 쓴다.
2. 설명 주석은 `# ←`, 개념 주석은 `# [개념]`으로 시작한다. 개념 주석은 1줄이다.
3. 개념 설명이 1줄보다 길면, 각주로 쓴다 (5.9절).
4. 데이터는 타입이 아니라 실제 값으로 쓴다.
5. 데이터 모양이 바뀌면, 바뀌기 전과 바뀐 뒤를 나란히 쓴다.
6. 반복문은 회차별 값을 표로 쓴다.
7. 함수 안에 갈래가 있으면, 단계 안에 작은 `flowchart`를 넣는다.
8. 외부 함수의 단계는 입력 값, 출력 값, "(추정)" 표시만 쓴다.

### 5.7 주의할 점

1. 아래 코드를 찾아 쓴다.
   - 부수효과가 있는 코드
   - 오류를 무시하는 코드
   - 순서나 시간에 의존하는 코드
   - 데이터를 잘라 내는 코드
   - 키가 없으면 오류가 나는 코드
2. 항목마다 지시를 먼저 쓴다. 이유는 다음 문장에 쓴다.
3. 예시에서 나온 항목에는 예시 이름과 단계 번호를 쓴다.
4. 예시가 지나가지 않은 중요한 코드도 이 절에 쓴다.

### 5.8 범위 밖

1. 설명하지 않은 함수와 파일을 쓴다. 이름마다 하는 일 1문장을 쓴다.
2. 다음에 설명할 흐름 1~2개를 제안한다.

### 5.9 각주

1. 개념이 본문에 처음 나오는 곳에 `[^키]`를 붙인다. 키는 영문 소문자와 하이픈이다.
2. 각주는 문서 맨 끝에 모은다.
3. 각주는 원어와 약자 풀이, 정의 1문장, 이 코드에서 하는 일 1문장, 짧은 예 1개 순서로 쓴다.
4. 각주는 코드 블록과 mermaid 밖의 문장에 붙인다.

## 6. 다이어그램 규칙

### 6.1 공통

1. 다이어그램 위에 핵심 메시지를 3문장 이하로 쓴다.
2. 다이어그램 아래에 "읽는 법"을 2문장 이하로 쓴다.
3. 노드 라벨에는 이름과 하는 일을 함께 쓴다.
4. 선에는 넘기는 값이나 동작을 쓴다.
5. 노드는 20개 이하로 그린다. 20개를 넘으면 다이어그램을 나눈다.
6. 예시가 지나가지 않는 경로는 점선으로 그린다.
7. 노드 ID는 영문과 숫자로 쓴다. 라벨은 큰따옴표로 감싼다. 라벨 안에서는 작은따옴표를 쓴다.
8. 라벨 안 줄바꿈은 `<br/>`로 쓴다.
9. 같은 대상은 모든 다이어그램, 표, 본문에서 같은 이름으로 쓴다.

### 6.2 시퀀스 다이어그램

1. 첫 줄에 `autonumber`를 쓴다. 번호는 단계 설명의 번호와 같다.
2. 참여자 이름: 1줄은 함수 이름, 2줄은 역할이다. 예: `participant SS as status_summary()<br/>상황 요약`.
3. 호출 화살표에는 넘기는 값을 쓴다. 예: `root = '/work/demo'`.
4. 반환 화살표에는 반환값 요약을 쓴다. 예: `요약 10줄, 402자`.
5. 값의 변화와 판단은 `Note`로 쓴다. 예: `Note over F: 9,551자 > 9,500자. 2차로 간다`.
6. 반복문은 `loop`, 조건 분기는 `alt`로 쓴다.

### 6.3 데이터 변환도

1. `flowchart LR`로 그린다.
2. 노드는 데이터 1개다. 1줄은 변수 이름과 타입, 2줄은 실제 값 일부다.
3. 선에는 데이터를 바꾸는 코드 줄과 동작을 쓴다. 예: `-->|"44행: 상태별로 묶음"|`.

## 7. 문장 규칙 (ASD-STE100 한국어판)

문서, 다이어그램 글자, 사용자 응답에 이 규칙을 적용한다.

### 7.1 단어

1. 한 대상에는 용어 1개만 쓴다. 한 용어에는 뜻 1개만 준다.
2. 동의어를 섞지 않는다. 예: "출력"을 쓰면 "결과", "반환물"을 쓰지 않는다.
3. 새 용어와 약자는 처음 나올 때 뜻을 쓴다.
4. 금지 단어: "적절히", "등", "여러", "약간", "알아서", "~것 같다", "다양한".
5. 지시어 대신 대상 이름을 쓴다. 예: "이것을 넘긴다" 대신 "`root`를 넘긴다".
6. 동사를 명사로 바꾸지 않는다. 예: "확인을 수행한다" 대신 "확인한다".
7. 비유와 관용구를 쓰지 않는다.
8. 실행 경우는 "예시"라고 부른다.

### 7.2 문장

1. 절차 문장은 20어절 이하, 설명 문장은 25어절 이하로 쓴다.
2. 한 문장에 동작 1개만 쓴다. "~하고", "~하며"로 동작을 잇지 않는다.
3. 능동형으로 쓴다.
4. 주어가 바뀌면 주어를 쓴다. 예: "`session()`이 `fit()`을 호출한다."
5. 조건은 문장 앞에 쓴다. 예: "길이가 9,500자를 넘으면, `fit()`이 요약을 줄인다."
6. 이중 부정을 쓰지 않는다.

### 7.3 문단과 목록

1. 문단 1개에 주제 1개, 6문장 이하로 쓴다.
2. 순서가 있으면 번호 목록, 순서가 없으면 글머리표 목록을 쓴다.

## 8. 점검

1. 함수 이름과 줄 번호를 원본 코드와 비교한다.
2. 수치를 계산 스크립트로 다시 계산한다.
3. 단계의 출력과 다음 단계의 입력이 같은지 확인한다.
4. 시퀀스 다이어그램 번호와 단계 설명 번호가 같은지 확인한다.
5. 단계 설명마다 원본 코드가 있는지 확인한다.
6. 독자의 순서로 문서를 처음부터 끝까지 읽는다. 설명이 끊기는 곳을 고친다.
7. mermaid 문법을 6절과 비교한다. 렌더링 도구가 있으면 렌더링한다.
8. 금지 단어와 25어절을 넘는 문장을 찾아 고친다.
9. 각주 키가 본문과 각주 목록에 모두 있는지 확인한다.
