## 🧩 UC-001 지정 대상 코드 설명서 만들기

- from: REQ-001
- actor: 사용자, worker
- status: approved

### ✅ 성공 흐름
- M0 사용자가 대상과 모드(스크립트 모드 또는 흐름 모드)를 정한다
- M1 worker가 `code-flow-explainer` 스킬로 대상 코드를 읽는다
- M2 worker가 예시 2~4개와 예시 데이터를 정한다
- M3 worker가 예시 값을 코드 한 줄씩 따라간다
- M4 worker가 따라간 값으로 설명서 1개를 쓴다
- M5 worker가 설명서를 `out/code_docs/`에 저장한다

### ⚠️ 실패 흐름
- E1 (M3) 외부 함수의 코드가 없다 → 출력을 추정하고 "(추정)"과 근거 줄 번호를 쓴다

### 🏁 성공조건
- 지정한 대상 1개에 설명서 1개가 `out/code_docs/`에 있다
- worker가 대상 코드와 실제 증권사 API(`src/kis/`, `kis_broker.py`)를 실행하지 않았다
- 설명서의 수치는 계산 스크립트 결과에서 나왔다

## 🧩 UC-002 src 코드 옮기기

- from: REQ-002
- actor: 사용자, worker
- status: approved

### ✅ 성공 흐름
- M1 worker가 `src/`의 파일마다 클래스와 함수의 성격을 읽는다
- M2 worker가 새 폴더 구조와 옮길 목록을 만든다
- M3 사용자가 구조와 목록을 승인한다
- M4 worker가 목록대로 코드를 옮긴다
- M5 worker가 모든 import를 새 위치로 고친다

### ⚠️ 실패 흐름
- E1 (M4) 옮기면 순환 import가 생긴다 → 그 항목을 옮기지 않고 보고한다

### 🏁 성공조건
- 승인한 목록의 항목이 모두 새 위치에 있다
- 옮긴 코드의 내용이 옮기기 전과 같다 (위치와 import만 다르다)

## 🧩 UC-003 칼만 OFI 전략 한 사이클 발전

- from: REQ-003
- actor: 사용자, worker
- status: approved

### ✅ 성공 흐름
- M0 사용자가 각 node의 대상 전략 버전을 정한다 (분석할 버전, 만들 버전)
- M1 worker가 이전 버전의 수집 데이터와 코드로 성능을 분석하고 분석서를 쓴다
- M2 worker가 분석서를 바탕으로 사용자와 설계방향을 논의한다. 프로젝트 매니저는 질문과 답을 그대로 전달한다
- M3 worker가 논의 결과로 설계 방향서를 쓰고, 사용자가 승인한다
- M4 worker가 설계 방향서대로 전략과 필요한 지표를 md 문서로 설계한다
- M5 사용자가 설계 문서를 승인한다
- M6 worker가 설계대로 indicator 코드를 만든다
- M7 사용자가 indicator로 데이터를 수집한다
- M8 worker가 설계대로 strategy 코드를 만든다
- M9 사용자가 다음 사이클을 지시하면 M0부터 다시 한다

### ⚠️ 실패 흐름
- E1 (M6) 설계한 지표를 현재 인터페이스로 만들 수 없다 → 설계 문서에 제약을 적고 M4를 다시 한다

### 🏁 성공조건
- 같은 버전 번호의 분석서, 설계 방향서, 설계서가 md로 있다
- 같은 버전 번호의 indicator와 strategy 코드가 프로젝트 인터페이스에 맞게 있다
- 이전 버전의 결과물이 바뀌지 않았다
